# 기획과 디자인을 만드는 작업 방식

Prototyper가 intent부터 prototype까지 책임지고 Builder가 기술적으로 참여한다. 시온은 기획의 근거, 프레이는 경험과 시각의 일관성을 책임진다. 레퍼런스의 형태를 복제하거나 기획 문서를 길게 만드는 것이 완료 조건이 아니다.

## 1. 의도에서 콘셉트로

- 사용자 원문, 현재 해결 방법, 불편이 발생하는 순간, 원하는 변화, 제약을 읽는다.
- 사용자에게 어려운 도구·아키텍처·마케팅 용어 선택을 먼저 떠넘기지 않는다. 꼭 필요한 질문을 짧게 하고 이미 말한 내용을 반복해서 묻지 않는다.
- `고객 → 상황 → 지금의 행동 → 제안하는 행동 → 얻는 결과`를 한 시나리오로 쓴다.
- 대안이 실제로 도움이 될 때만 비교한다. 항상 3개 아이디어를 채우지 않는다. 다른 대안은 색이 아니라 해결 방식·고객의 노력·가치 전달에서 차이가 있어야 한다.
- 선택안의 장점뿐 아니라 포기하는 것과 반증 가능한 가정을 기록한다. 고객 증거가 없으면 가설로 유지한다.
- 핵심 과업을 설명할 수 없으면 기능 목록 확장 대신 콘셉트를 다시 정리한다.

## 2. 콘셉트에서 디자인 방향으로

레퍼런스마다 출처와 확인한 범위를 남긴다. 실제 열지 못한 링크는 미확인이다.

| 항목 | 기록할 내용 |
| --- | --- |
| 관찰 | 정보 배치, 타이포그래피, 밀도, 이미지, 행동, 동작에서 실제로 본 것 |
| 해석 | 왜 이 제품의 고객·과업에 적합한지 |
| 적용 | 어떤 원리를 어떤 화면에 적용할지 |
| 제외 | 원본의 어떤 표현은 가져오지 않을지 |
| 검증 | 실제 화면에서 무엇을 비교할지 |

제품 콘셉트에 맞는 정보 구조를 먼저 정한다. 카피는 실제 고객 언어와 콘텐츠 길이로 작성한다. 임시 카피·이미지는 표시하고 최종 디자인인 것처럼 승인받지 않는다.

시각 방향에는 표면, 글자 역할과 크기 관계, 색의 의미, 여백, 형태, 이미지 역할, 동작의 목적을 적는다. 고정 폰트·색·섹션 순서·CTA 개수·카드 수를 모든 제품에 적용하지 않는다. 이미 선택한 디자인 시스템은 유지한다.

## 3. 대표 장면부터 실제로 구현

제품의 가치를 가장 잘 드러내거나 구현 불확실성이 큰 장면을 고른다. 홈 화면이 항상 우선은 아니다. 예를 들어 대화형 제품은 입력 → 반응 → 결과 확인을 먼저 구현한다.

Builder와 함께 데이터·연동·렌더링·성능 제약을 확인한다. 원래 콘셉트가 불가능하면 구현 가능한 대안과 품질 차이를 제시한다. 조용히 다른 디자인으로 바꾸지 않는다.

- 진입, 핵심 행동, 완료 뒤 다음 행동을 연결한다.
- 해당 과업에 필요한 로딩·빈 상태·오류·재시도·중단·복원 상태를 포함한다.
- 실제 내용 또는 명확히 표시한 예시를 사용한다.
- 데스크톱과 모바일의 실제 렌더를 확인하고, 해당 환경에서 핵심 행동을 수행한다.
- 장식·애니메이션이 핵심 과업을 가리지 않게 한다. 결과는 준비되는 즉시 접근 가능하게 한다.
- 참고 이미지와 실제 시제품을 구분한다. 이미지 생성만으로 동작하는 시제품을 만들었다고 보고하지 않는다.
- 입력·업무 상태를 화면 연출과 분리한다. 가짜 조사·리뷰·완료 표시를 만들지 않는다.

범위가 작은 작업은 기존 대표 화면과 승인 기록을 재사용한다. 같은 자료를 다시 만드는 단계를 강제하지 않는다.

## 4. 사람의 피드백을 수정 작업으로 전환

“별로다”를 받으면 가능한 원인을 화면과 함께 좁힌다. 판단에 필요한 질문 하나 또는 수정 방향의 작은 비교본을 준비한다. 전체를 무작정 재생성하지 않는다.

| 피드백 종류 | 돌아갈 책임 | 수정할 대상 |
| --- | --- | --- |
| 제품의 필요성·제안이 약함 | Prototyper / 시온 | 문제와 콘셉트 |
| 무엇을 해야 할지 모르겠음 | Prototyper / 프레이 | 정보 구조·행동·카피 |
| 분위기·위계·밀도가 의도와 다름 | Prototyper / 프레이 | 시각 방향·대표 화면 |
| 의도는 맞지만 화면이 깨지거나 동작이 틀림 | Builder + Sweeper | 구현 |
| 반응·재사용·구매 근거가 약함 | Grower + Prototyper | 실험과 가설 |

각 수정에는 원문, 해석, 변경 대상, 유지할 결정, 전후 비교를 남긴다. 역할이 바뀌어도 사용자의 이전 선택을 잊지 않는다.

## 5. 경험을 구현으로 넘기는 기준

핵심 시나리오, 대표 화면 버전, 카피, 상태별 행동, 시각 원칙, 자산 출처, 확인한 기술 제약과 미확인 부분을 전달한다. Builder는 승인된 시제품과 결과를 대조하며 확장한다. 인계 후에도 Prototyper가 설계 의도에 관한 질문을 책임진다.

Sweeper는 아래 기준을 증거로 확인한다. 단순 점수 평균으로 중요한 실패를 숨기지 않는다.

| 기준 | 확인 방법 |
| --- | --- |
| 기획의 구체성 | 고객·상황·변화·선택 이유를 실제 콘텐츠에서 확인 |
| 핵심 행동의 명확성 | 처음 진입해 다음 행동과 결과를 이해할 수 있는지 관찰 |
| 정보 위계 | 주요 내용과 보조 내용이 글자·배치·카피에서 구분되는지 확인 |
| 제품 고유성 | 레퍼런스 해석과 제품 콘셉트가 실제 표현에 반영됐는지 비교 |
| 일관성과 완성도 | 연결 화면, 실제 콘텐츠 길이, 빈 상태·오류·복원 확인 |
| 접근과 사용 가능성 | 키보드, 포커스, 대비, 좁은 화면, 동작 줄이기 확인 |
| 구현 충실도 | 선택된 시제품과 실제 동작·표현의 차이 확인 |

검토는 pass / revise / unverified와 근거를 남긴다. 주관적인 선호는 사람의 선택 항목으로 분리하고, 증거 없는 사용자 사용성 검증을 주장하지 않는다.
